# 09.用户与权限模块设计说明（对齐需求分析文档 v2.2）

> 项目：基于AI的大学生就业服务智能体（AiStudentJobAgent）
> 模块：用户与权限管理 · 组员 2（RBAC 权限）
> 对齐依据：《第3组需求分析文档 v2.2》——数据库共 8 张表 / 116 个数据项，无独立角色/菜单表
> 技术栈：Java 17 + Spring Boot 3.5 + MyBatis-Plus + MySQL 8 + Spring Security(JWT)

---

## 一、设计口径变更说明（重要）

此前交付的版本引入了 4 张独立权限表（`sys_role / sys_menu / sys_user_role / sys_role_menu`）。
经与团队需求分析文档 v2.2 核对，**该方案与团队统一口径冲突**，已废弃：

| 维度 | 旧方案（已废弃） | 新方案（对齐 v2.2，现采用） |
|---|---|---|
| 表结构 | 新增 4 张权限表，共 12 张表 | **保持 8 张表**，不新增表 |
| 角色来源 | sys_role 表 + 关联表 | `sys_user.role_code`（RoleCodeEnum 枚举） |
| 权限控制 | @RequiresPermission(perm_code) | 角色识别 + 菜单权限过滤 + 数据范围隔离 + 接口级鉴权 |
| 菜单管理 | sys_menu 树 + 角色-菜单关联 | 前端按 role_code 硬编码动态渲染（文档图-14「菜单权限过滤」） |

> 结论：权限方案 = **「用户(1 表) × 角色(枚举字段) × 权限(三重控制)」**，与队友的 8 表数据模型完全一致，无表结构冲突。

## 二、权限模型（对齐文档 5.2 / 图-14）

### 2.1 角色与数据范围（文档 5.2 角色职责与权限表）

| 角色编码 | 角色名称 | 数据范围 | 典型权限 |
|---|---|---|---|
| STUDENT | 学生 | 仅本人数据 | 完善档案、简历诊断、岗位匹配投递、实习申请、面试训练、政策咨询 |
| COUNSELOR | 辅导员 | 所辖班级数据 | 查看学生档案与就业进展、审批实习、批阅日志、发布岗位、查看咨询热点 |
| HR | 企业HR | 本企业岗位与相关申请 | 发布/下线岗位、处理投递申请、企业导师审批与评价 |
| COLLEGE_ADMIN | 院系管理员 | 全院数据 | 全院看板、岗位与流程管理、实习终审、政策库维护 |

角色编码取值与 `SysUser.RoleCode`、`RoleCodeEnum` 一致（文档 6.4 状态枚举码表）。

### 2.2 权限控制链路（文档 图-14 功能架构子图）

```
登录身份校验 → 角色识别(RoleCheck) → 菜单权限过滤 → 数据权限控制 → 安全校验(接口级鉴权)
```
- **登录身份校验**：JWT 令牌有效性、密码策略过滤（沿用现有 Spring Security + JWT）。
- **角色识别 RoleCheck**：读取 `SecurityUtils.getRoleCode()`。
- **菜单权限过滤**：前端路由/菜单按 `role_code` 硬编码映射动态渲染；后端接口按角色放行。
- **数据权限控制**：业务 SQL 按角色 + 归属字段过滤（学生仅本人、辅导员仅所辖班级、HR 仅本企业）。
- **接口级鉴权**：除登录注册等公开接口外，所有接口校验令牌；越权返回 401 / 403（文档 4.2 安全性）。

## 三、接口级鉴权实现（成员2核心交付）

### 3.1 角色校验注解 @RequiresRole + AOP 切面

在后端 Controller 方法上标注即可，由切面读取当前登录用户角色做校验：

```java
// 仅辅导员可审批实习
@RequiresRole("COUNSELOR")
public Result<Void> review(...) { ... }

// 辅导员或院系管理员均可（满足其一）
@RequiresRole(value = {"COUNSELOR", "COLLEGE_ADMIN"}, anyOf = true)
public Result<Void> publishJob(...) { ... }
```

- 超级权限：`COLLEGE_ADMIN` 为全院级角色，其接口放行逻辑按业务在 Service 层结合数据范围判断。
- 无权限抛 `BizException.of(ResultCode.FORBIDDEN)` → 403（需确认 `ResultCode.FORBIDDEN` 存在）。

### 3.2 数据范围隔离规范（对齐文档 6.5 跨表一致性）

数据范围在 **Mapper/SQL 层**完成，不在接口层硬塞。规范示例：

| 角色 | 过滤依据 | 示例 SQL 条件 |
|---|---|---|
| STUDENT | `student_id = 当前用户id` | `WHERE student_id = #{userId}` |
| COUNSELOR | 班级归属 | `WHERE college = #{loginUser.college}`（或按班级表） |
| HR | 本企业 | `WHERE publisher_id = #{userId}` |
| COLLEGE_ADMIN | 不过滤（全院） | 无归属条件 |

统一用 `SecurityUtils.getUserId()` / `SecurityUtils.getRoleCode()` 取当前上下文，禁止在业务代码里手动解析 token。

### 3.3 查看自身权限接口

模块1 FR-1 中「查看自身权限」由后端返回当前用户角色与权限范围：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/system/me/permissions` | 返回当前用户 `role_code / role_name / dataScope` |

## 四、权限相关 SQL（对齐 v2.2）

**无需新增任何权限表**。权限完全复用现有 `sys_user.role_code`：

1. `sys_user` 表结构（已含 role_code，无需改动）：
```sql
-- 用户表（已存在，18 个数据项）
CREATE TABLE sys_user (
    id          BIGINT NOT NULL AUTO_INCREMENT,
    username    VARCHAR(32)  NOT NULL,
    password    VARCHAR(100) NOT NULL,
    real_name   VARCHAR(32),
    role_code   VARCHAR(20)  NOT NULL COMMENT 'STUDENT/COUNSELOR/HR/COLLEGE_ADMIN',
    -- ...（其余字段见 schema.sql）
);
```

2. 演示账号角色初始化（若 `data.sql` 未包含）：
```sql
-- 确保四个演示账号角色正确
UPDATE sys_user SET role_code='STUDENT'      WHERE username='student01';
UPDATE sys_user SET role_code='COUNSELOR'    WHERE username='counselor01';
UPDATE sys_user SET role_code='HR'           WHERE username='hr01';
UPDATE sys_user SET role_code='COLLEGE_ADMIN'WHERE username='admin01';
```

3. 按角色查询用户（管理/验收用）：
```sql
SELECT id, username, real_name, role_code, status FROM sys_user ORDER BY role_code;
```

## 五、表结构合并到整体数据模型

- 数据模型维持团队统一的 **8 张表 / 116 个数据项**（文档 6.2），**不新增表**。
- `sys_user` 是权限唯一载体：`role_code` 承担角色，`status` 承担账号启用/停用（FR-1.4），`deleted/create_time/update_time` 为公共数据项。
- 与其他模块协作：各业务表通过 `student_id / publisher_id / mentor_id / teacher_id` 关联 `sys_user`（文档 6.5 跨表一致性），权限在查询时按角色过滤归属字段，**不改变任何队友建的表结构**。

## 六、验证与风险
- **编译验证**：`RequiresRole` + `RoleAspect` 依赖现有 `SecurityUtils.getRoleCode()`、`Result`、`BizException`；需确认 `ResultCode.FORBIDDEN` 存在，否则在 `ResultCode` 补充 `FORBIDDEN(40300, "无权限访问")`。
- **兼容性**：与现有 `AuthController`（注册/登录/me）无缝衔接；`me` 已返回用户信息含 role_code。
- **口径一致性**：本方案与需求文档 8 表模型、图-12/图-14、5.2 角色表完全对齐，无需与队友协调表结构。

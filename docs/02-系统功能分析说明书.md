## 1. 引言

### 1.1 编写目的

本文档面向项目组、指导教师与验收人员，明确系统的**用户角色、功能边界、业务流程、非功能约束与验收标准**，
作为后续《系统详细设计》《系统接口设计》《系统测试》与编码实现的依据。

### 1.2 项目背景

高校毕业生就业服务涉及简历指导、岗位对接、实习管理、面试训练与政策咨询等多个环节，传统模式依赖人工，
存在"简历无人指导、岗位匹配靠手工筛选、实习审批留痕难、政策咨询重复问答"等痛点。
本系统以大模型智能体为核心，构建面向学生、辅导员、企业 HR 与院系管理员的一体化就业服务平台。

### 1.3 术语定义

| 术语 | 含义 |
| --- | --- |
| 智能体（Agent） | 以大模型为核心能力、可调用业务数据与工具完成特定任务的服务单元 |
| 简历诊断 | 智能体对简历内容给出优势、不足、修改建议与缺失关键词的过程 |
| 岗位匹配度 | 由技能、学历、专业、地域意向、档案完整度五个维度加权计算得到的 0-100 分 |
| 流程节点 | 实习审批流程中的状态，包括企业导师审批、辅导员审批、院系管理员审批 |
| 节点回退 | 审批驳回时，流程退回上一节点而不是直接终止（首节点驳回除外） |
| 本地规则引擎 | 未配置大模型或模型调用失败时启用的确定性规则实现，保证功能可用 |
| 政策引用 | 政策问答回答中标注的政策来源编号，对应 `policy_item` 表中的具体条目 |

## 2. 系统概述

### 2.1 建设目标

1. 为学生提供"简历—岗位—实习—面试—政策"全链路就业服务；
2. 用智能体替代重复性人工工作（简历初筛建议、岗位匹配说明、面试点评、政策问答）；
3. 为辅导员与院系管理员提供数据看板与流程审批能力，实现就业工作可量化、可追踪。

### 2.2 用户与角色

| 角色 | 用户画像 | 核心诉求 |
| --- | --- | --- |
| 学生 | 在校生（本科 / 硕士） | 找岗位、改简历、练面试、办实习、问政策 |
| 辅导员 | 班级指导教师 | 掌握班级就业情况、审批实习、批阅日志、精准帮扶 |
| 企业 HR | 招聘负责人 | 发布岗位、筛选简历、跟踪投递、评价实习生 |
| 院系管理员 | 就业工作管理者 | 全院数据统计、岗位与流程管理、政策库维护 |

### 2.3 运行环境

- 服务端：JDK 17、Spring Boot 3.5、MySQL 8、Redis 7、Docker 24+
- 客户端：Chrome / Edge / Firefox 等主流浏览器（PC 优先，兼容移动端 H5）

## 3. 功能需求

### 3.1 用户与权限管理模块

| 编号 | 需求 | 说明 | 实现状态 |
| --- | --- | --- | --- |
| FR-1.1 | 四类角色注册与登录 | 学生、辅导员、企业 HR、院系管理员 | 已实现（`/api/auth/register`、`/api/auth/login`） |
| FR-1.2 | 角色权限精细控制 | 菜单可见性与接口访问双重控制，数据相互隔离 | 已实现（JWT + `@PreAuthorize` + 数据归属校验） |
| FR-1.3 | 学生个人档案 | 基本信息、教育背景、技能证书、求职意向 | 已实现（`/api/users/me`） |

> 权限模型说明：题目要求"基于苍穹权限模型实现角色权限精细控制"。本项目采用企业级 RBAC 语义实现：
> **用户 → 角色 → 菜单权限 + 数据权限**。菜单权限由角色编码与 `@PreAuthorize` 表达式控制；
> 数据权限在 Service 层按角色过滤（学生仅见本人数据、辅导员见所辖班级、管理员见全院）。

### 3.3 岗位匹配与申请模块

| 编号 | 需求 | 说明 | 实现状态 |
| --- | --- | --- | --- |
| FR-3.1 | 岗位发布 | 企业 HR / 辅导员发布岗位（名称、要求、薪资、截止日期） | 已实现（`POST /api/jobs`） |
| FR-3.2 | 岗位检索 | 关键词、类别、城市筛选 + 分页 | 已实现（`GET /api/jobs`） |
| FR-3.3 | 智能匹配 | 返回匹配分数、等级、命中/缺失技能、打分依据与智能体解读 | 已实现（`GET /api/jobs/{id}/match`） |
| FR-3.4 | 一键投递 | 防重复投递，记录投递时匹配分 | 已实现（`POST /api/jobs/{id}/apply`） |
| FR-3.5 | 投递进度跟踪 | 学生查看本人投递；HR 查看岗位申请并更新状态 | 已实现（`/api/jobs/my/applications`、`/api/jobs/applications/{id}/status`） |

**岗位匹配算法（可解释）**：总分 100 分 = 技能匹配 40 + 学历 15 + 专业关联 15 + 地域意向 15 + 档案完整度 15。
分数由规则计算（可复现、可解释），智能体仅负责生成自然语言的匹配解读与投递建议。

### 3.4 实习管理模块

| 编号 | 需求 | 说明 | 实现状态 |
| --- | --- | --- | --- |
| FR-4.1 | 实习申请流程 | 企业导师 → 辅导员 → 院系管理员 三级审批，支持节点回退 | 已实现（`POST /api/internships/{id}/approve`） |
| FR-4.2 | 流程留痕 | 每次流转记录操作人、动作、节点、意见、时间 | 已实现（`flow_trace_json` + 前端时间轴） |
| FR-4.3 | 实习日志提交 | 学生按周提交日志 | 已实现（`POST /api/internships/{id}/logs`） |
| FR-4.4 | 日志批阅 | 辅导员批阅留言并打分，同时生成智能体点评 | 已实现（`POST /api/internships/logs/{logId}/review`） |
| FR-4.5 | 三方评分汇总 | 学生自评 20% + 企业导师 40% + 校方 40% | 已实现（`POST /api/internships/{id}/scores`） |

**流程状态机**：

```text
提交申请 → MENTOR_REVIEW（企业导师）
              ├─ 通过 → COUNSELOR_REVIEW（辅导员）
              │           ├─ 通过 → COLLEGE_REVIEW（院系管理员）
              │           │           ├─ 通过 → PASSED（归档）
              │           │           └─ 驳回 → COUNSELOR_REVIEW（回退）
              │           └─ 驳回 → MENTOR_REVIEW（回退）
              └─ 驳回 → REJECTED（终止）
```

## 4. 典型用例描述

### UC-01 用户登录

| 项 | 内容 |
| --- | --- |
| 参与者 | 全部角色 |
| 前置条件 | 已在系统中注册且账号状态为启用 |
| 基本流程 | 1) 输入账号密码 → 2) 系统校验账号与 BCrypt 密码 → 3) 校验账号状态 → 4) 签发 JWT 并返回用户信息与角色 |
| 异常流程 | 账号不存在或密码错误 → 返回 60003；账号被停用 → 返回 60004 |
| 后置条件 | 前端保存令牌，后续请求携带 `Authorization: Bearer <token>` |

### UC-05 简历 AI 诊断

| 项 | 内容 |
| --- | --- |
| 参与者 | 学生 |
| 前置条件 | 已登记简历（含正文或附件） |
| 基本流程 | 1) 学生点击"AI 诊断" → 2) 系统组装简历正文与目标岗位 → 3) 调用智能体 → 4) 返回总分、等级、优势、不足、建议、缺失关键词 → 5) 报告落库 |
| 异常流程 | 大模型不可用 → 自动降级本地规则引擎，接口仍正常返回（`engine=local-rule`） |
| 业务规则 | 评分区间 40-96；诊断报告可回看，便于对比修改前后得分 |

### UC-09 岗位投递

| 项 | 内容 |
| --- | --- |
| 参与者 | 学生 |
| 前置条件 | 已登录且角色为学生；岗位处于招聘中 |
| 基本流程 | 1) 学生查看岗位 → 2) 执行智能匹配（可选） → 3) 一键投递 → 4) 系统校验岗位状态与重复投递 → 5) 生成申请记录（状态 SUBMITTED） |
| 异常流程 | 岗位已下线 → 60021；重复投递 → 60022 |
| 业务规则 | 投递时记录匹配分，便于后续复盘与统计 |

### UC-12 实习多级审批

| 项 | 内容 |
| --- | --- |
| 参与者 | 辅导员 / 企业 HR / 院系管理员 |
| 前置条件 | 存在状态为 RUNNING 的实习申请 |
| 基本流程 | 1) 审批人查看待办 → 2) 选择通过或驳回并填写意见 → 3) 系统按状态机流转节点 → 4) 追加流程轨迹 |
| 异常流程 | 申请已结束（PASSED/REJECTED）→ 60030 |
| 业务规则 | 通过 = 前进一节点；驳回 = 回退一节点；首节点驳回 = 终止 |

### UC-15 AI 面试训练

| 项 | 内容 |
| --- | --- |
| 参与者 | 学生 |
| 前置条件 | 已登录；选择场景与题量 |
| 基本流程 | 1) 开始训练生成题目 → 2) 逐题作答 → 3) 系统按三维度评分并给出改进示范 → 4) 结束训练生成报告 |
| 业务规则 | 三维度各 0-100，总分取三维均分；报告中包含历史对比所需字段 |

### UC-18 政策智能问答

| 项 | 内容 |
| --- | --- |
| 参与者 | 学生（其余角色亦可查看政策库） |
| 前置条件 | 政策库已初始化 |
| 基本流程 | 1) 学生提问 → 2) 系统检索 Top-K 相关政策 → 3) 智能体基于政策原文作答并标注 [序号] → 4) 返回回答与引用列表 → 5) 记录提问用于热点统计 |
| 异常流程 | 政策库无匹配 → 明确告知"未收录，建议咨询就业指导中心"，不编造政策 |
| 业务规则 | 回答必须可溯源；引用包含政策标题、发布单位、发布日期 |

## 5. 业务流程

### 5.1 学生求职闭环

```text
完善档案 → 登记/上传简历 → AI 简历诊断并修改 → 浏览岗位 → 智能匹配 → 一键投递
        → 跟踪进度（已查看/面试/录用） → AI 面试训练 → 政策与权益咨询
```

### 5.2 实习全流程

```text
学生提交申请 → 企业导师审批 → 辅导员审批 → 院系审批通过
            → 学生按周提交日志 → 辅导员批阅（含智能体点评）
            → 实习结束 → 学生自评 + 企业导师评价 + 校方评定 → 加权汇总分
```

### 5.3 智能体调用链

```text
业务 Service → AgentOrchestrator（场景路由）
             ├─ 大模型通道：PromptLibrary → OpenAiCompatibleLlmClient → 结构化 JSON
             └─ 降级通道：LocalRuleEngine → 确定性规则结果（engine=local-rule）
```

## 6. 非功能需求

| 类别 | 需求 | 落地方式 |
| --- | --- | --- |
| 性能 | 常规接口响应 < 1s；AI 接口 < 15s；分页上限 200 条 | 索引优化、分页插件、AI 超时可配置 |
| 安全 | 密码 BCrypt 存储；JWT 无状态认证；接口级鉴权；越权校验 | Spring Security + `@PreAuthorize` + 归属校验 |
| 可靠性 | 依赖不可用时业务不中断 | 大模型失败降级规则引擎；Redis 异常降级直查数据库 |
| 可用性 | 界面符合中文用户习惯，关键操作有提示与确认 | Element Plus 组件 + 统一错误提示 |
| 可维护性 | 分层清晰、命名规范、注释完整、接口文档自动生成 | 见《项目开发规范》，Swagger 文档 |
| 兼容性 | PC 主流浏览器；移动端可访问 | 响应式布局 + 标准 Web 技术 |
| 可部署性 | 一条命令完成部署 | Docker Compose（MySQL + Redis + 后端 + 前端） |

## 8. 验收标准

1. 四类角色均可正常登录，且只能访问授权菜单与数据；
2. 学生可完成"完善档案 → 简历诊断 → 岗位匹配 → 投递 → 面试训练 → 政策问答"闭环；
3. 辅导员可完成实习审批（含节点回退）与日志批阅；
4. 数据看板三个核心图表数据与数据库一致；
5. 政策问答回答带来源引用，政策库条目不少于 50 条；
6. 断网或无模型密钥时系统仍可完整演示（自动降级）；
7. `docker compose up -d --build` 后 4 个容器均健康，前端可访问。
